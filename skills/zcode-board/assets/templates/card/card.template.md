## 条目形态（计划稿内逐字段；缩进两空格）

```markdown
- [ ] <标签> <标题> <!-- zcode-board: no=<稳定号> -->
  责任: <单一角色——implementer / test-verifier / code-reviewer / ui-designer / code-explorer / debugger / refactoring-optimizer>
  目标: <一句话目标；改动面点名列文件/模块；范围收口口径>
  交付面全量枚举: <必填段①——主件 + 全部配套件，逐项点名>
  用户原话引用: <必填段②——访谈 id + 用户原话引号原文 + 裁决拍板引句>
  验收: <用户视角句——用户看到/点到什么；正常路径 + 反例/突变各一>
  > blocked-by: <稳定号>          （可选；未发号占位用 `> blocked: 等待 …拆卡后补号`，发号后替换）
  > agents: <角色>                （可选；显式覆盖责任管线时，形态同既有卡）
```

- 未领号草稿不写 `<!-- zcode-board: no=… -->` 标记；号由编排者 `--assign` 补写，人不得手写。
- 条目正文与其续行（含 `>` 标记行、执行注记）必须保持缩进；条目之间空行分隔。

## 必填段①「交付面全量枚举」

- 拆卡前先枚举用户意图的**全量交付面**：主件 + 配套件（提示词 / hook / 技能 / 文档 / 分发配套件），再由完整范围按文件域与可验证中间产物拆成可并行卡、同批收口。
- **拆粒度不砍范围**（裁决③）：禁止以"卡太大/避免超长"为由收窄范围；砍范围必须用户明示裁决（E1 V16：P2 教训——UI 开关发了、注入三位一体被砍，用户在新项目裸奔踩坑）。
- 粒度分割本身照 SKILL.md §6.11：预估 >30 分钟必须再拆；>60 分钟禁止整卡派发。
- 枚举形态逐项点名（供收口核对）：①<主件>；②<测试/夹具与反例断言>；③<文档/提示词>；④<分发配套件>；⑤<与相邻卡的接口注记> …

## 必填段②「用户原话引用」

- 必须带**访谈 id + 用户原话（引号原文）**：只给摘述/转译不算（E1 V14/V15；2026-10-10 用户批准的规格纪律）——转译比原话窄是 plan-reviewer 的 finding。
- 原话可来自：用户反馈（`itw-*` 登记）、裁决包/纲要中的拍板引句、既有卡文引语；引用时同时点明来源。
- 相关裁决与事件号一并点名（如 E1 V14/V15/V16），便于 plan-reviewer 逐句对照。

## 验收段句式

- 主语是用户/评审人，动作是"**看到/点到/打开/跑一条命令得到**"，结果可机械对照（被拦/被点名/消失/呈现/留档）。
- 至少覆盖：正常路径（绿）+ 一个反例或突变（红）——断言/hook 类卡必须带突变或反例断言（E4-24）。
- 与「交付面全量枚举」配套件逐项对账：验收可回溯到交付面条目。

## 反例（不得按此派发的形态）

- 缺「交付面全量枚举」→ 见 card.example-fail.md（对照样本，供缺段校验比对）。
- 缺「用户原话引用」或仅有摘述 → 同属缺段。
- 验收句无用户视角（如只写"改动完成/测试通过"）→ 句式不合规。
