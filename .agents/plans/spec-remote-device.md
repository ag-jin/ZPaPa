# Spec：远程设备（Remote Device）

> 状态：ready-for-agent
> 领域词汇：见 `CONTEXT.md` → 「远程设备投射（Remote Device Projection）」节
> 决策来源：Q1–Q19 审问（全部经用户确认）

## Problem Statement

用户有两台机器（A：日常开发机，B：另一台机器）。用户希望**在 A 上直接使用 B 的项目与会话**，但现在的远程能力不够用：

- 现在的远程流程必须**先选目录**才能连上，语义是"连一个项目"，不是"连一台设备"。
- 连上之后，**A 的侧边栏看不到 B 的项目**，也看不到 B 的会话 —— 用户最想要的能力缺失。
- 之前尝试过"把 B 的会话并入 A 的本地列表"的方案，需要在 A 端维护会话索引副本，并处理两套键名（A 用 `remote:ssh:...` 前缀、B 用纯路径）的映射与隔离，反复出问题（列表为空、键不匹配、写操作在对端留下重复索引行）。
- 用户在 B 本机跑过的会话，本应两端都能看到并继续；但 A 端没有任何入口。
- 用户也希望能调整 B 的设备设置（如显示思考过程、工作区记忆），但不想在 B 上手工改。

## Solution

把「连项目」改成「**连设备**」：

A 在设置页添加一台远程设备（主机、认证、密钥路径），连上后：

- **主区显示设备概览**：B 已添加的项目列表 + 各项目会话数 + 「添加项目」按钮。
- **侧边栏投射 B 的项目**（按 A 的设置勾选显示哪些），带远程图标区分来源。
- **点开项目进入工作区**：见到 B 的会话（排除已归档），点开即可查看并按需加载更早内容，也可直接在提交框继续对话 —— 执行发生在 B。
- **在 A 上添加 B 的新项目**：浏览 B 的文件系统选目录，登记到 B 的项目列表。
- **设置页可读写 B 的设备设置**（白名单字段），用产品原生文案展示。

**A 端只保留连接入口，不保留任何会话数据或索引。** 断开后侧边栏只留设备条目（灰显），点一下即重连；B 上的会话不受影响，B 本机可独立继续操作。

## User Stories

### 连接设备

1. 作为 A 的用户，我想在设置页添加一台远程设备（填主机、用户名、密钥路径），这样我不需要每次连接都重填 SSH 信息。
2. 作为 A 的用户，我想**不选目录**就能直接连上 B 的 ZCode，因为我要用的是整台设备而不是某个目录。
3. 作为 A 的用户，我想在设置页看到设备的连接状态（已连接 / 已断开），这样我知道当前能不能用。
4. 作为 A 的用户，我想点击已断开的设备条目就重连，不用再去设置页翻找。
5. 作为 A 的用户，我想在断开后仍看到设备条目（灰显），这样我知道"这台设备还在，只是没连上"。
6. 作为 A 的用户，我想连接失败时看到明确原因（认证失败 / B 的 ZCode 没开 / 网络不通），而不是一直转圈。

### 设备概览

7. 作为 A 的用户，我想连上后看到 B 的项目列表，这样我一眼知道 B 上有哪些项目可用。
8. 作为 A 的用户，我想看到每个项目的会话数，这样我能判断哪个项目最近在活跃使用。
9. 作为 A 的用户，我想从概览点进某个项目，进入该项目的完整工作区（文件树、会话列表、对话）。
10. 作为 A 的用户，我想在概览里看到「添加项目」入口，这样我能在 A 上登记 B 的新项目。
11. 作为 A 的用户，我想设备概览的刷新是实时的（从 B 拉取），而不是缓存的旧数据。
12. 作为 A 的用户，我想连接中断时概览给出明确提示，而不是停留在过期数据上。

### 项目投射

13. 作为 A 的用户，我想在设置里勾选显示哪些 B 的项目，这样侧边栏不会被不需要的项目塞满。
14. 作为 A 的用户，我想勾选的候选项就是 B 已添加的项目（含新登记但还没会话的），这样我添加后立刻能看到。
15. 作为 A 的用户，我想在设置里关掉某个项目时**只影响 A 的显示**，B 本机仍然照常可见可用。
16. 作为 A 的用户，我想侧边栏里 B 的项目有明确的来源标记（图标/颜色），这样我能区分哪些是本机项目、哪些是 B 的。
17. 作为 A 的用户，我想侧边栏断开态的项目灰显并标注已断开，点击即重连。
18. 作为 A 的用户，我想同时看到本机项目和 B 的项目（混在一个列表里），这样我不需要在两个地方找项目。

### 会话

19. 作为 A 的用户，我想看到 B 上某个项目的会话列表，这样我知道那边在聊什么。
20. 作为 A 的用户，我想**看不到已归档的会话**，因为归档的我不再关心。
21. 作为 A 的用户，我想点开会话就看最近的内容，这样我能快速接上下文。
22. 作为 A 的用户，我想往上滚动时自动加载更早的历史，这样我不用一次拉全部（单个会话可能有数百条消息）。
23. 作为 A 的用户，我想在 A 上直接继续 B 的会话（打字并发送），执行发生在 B，这样我在 A 也能推进那边的工作。
24. 作为 A 的用户，我想在 A 上新建的会话落在 B（归属 B、数据在 B），这样两端看到的是同一个会话，不会出现两份。
25. 作为 A 的用户，我想 A 断开后 B 本机能独立继续这些会话，因为对话本来就在 B 上，不需要依赖 A。
26. 作为 A 的用户，我想会话列表里的状态（运行中 / 完成 / 出错）如实反映 B 的真实状态。

### 添加远程项目

27. 作为 A 的用户，我想浏览 B 的文件系统来选目录，这样我不用手输路径、也不会输错。
28. 作为 A 的用户，我想选完目录后它登记到 B 的项目列表（发在 B，不是只在 A），这样 B 本机也能看到。
29. 作为 A 的用户，我想添加的项目立刻出现在设备概览与勾选候选里，这样我能马上用它。

### 设备设置

30. 作为 A 的用户，我想在设置页看到 B 的设备设置项，用与 B 本机相同的名称和说明，这样我不会以为两处是不同的开关。
31. 作为 A 的用户，我想能改这些设置项（如显示思考过程、工作区记忆），改动立即在 B 生效。
32. 作为 A 的用户，我想如果改动没生效（读回不一致）能明确看到，而不是 UI 显示成功但实际没变。
33. 作为 A 的用户，我想这些设置项只包含安全的白名单（不含凭据、路径、窗口尺寸这类设备本地属性），这样我不会误改危险配置。

### 边界与信任

34. 作为 A 的用户，我想 A 端**不存任何会话数据或索引**，这样不会出现"A 上有一份、B 上有一份"的分裂状态。
35. 作为 A 的用户，我想 A 端只保留连接入口（主机、认证、显示偏好），这样重连方便且不留下数据副本。
36. 作为 A 的用户，我想 B 设置里的任何改动都不受 A 的显示偏好影响，这样两台设备的职责边界清晰。
37. 作为 A 的用户，我想断开连接后 A 端不缓存 B 的项目清单，这样我不会把过期清单当成真实状态。
38. 作为 A 的用户，我想首版只连一台设备就够用，但不想将来加第二台时要重构。

## Implementation Decisions

### 模块与职责

- **连接生命周期**：现有远程 workspace 的建立/断开链路改造为**设备级**。当前流程要求先选目录才能完成连接绑定；改为连上即可用，目录不再参与连接前提。
- **设备概览**：主区新增一个设备视图，数据全部实时从被投射设备拉取（项目清单、会话数）。
- **侧边栏投射**：现有项目列表渲染扩展为可显示投射项目（连接态正常显示、断开态灰显），来源标记由数据上的来源字段驱动。
- **远程项目登记**：新增"浏览被投射设备文件系统 → 选目录 → 写入被投射设备的项目列表"路径。写入目标是**被投射设备的设置**，不是投射端。
- **设备设置投射**：已完成。白名单（排除法）+ 产品原生文案 + 写入读回确认。
- **会话内容加载**：会话打开按需拉取（先最近、上滚再取更早）。
- **会话续接**：打通"投射端发起 → 被投射设备执行"的链路。

### 关键约束（来自实测）

- **会话归属与执行都在被投射设备**：投射端不产生本地副本，也不在本地执行模型调用。已验证：投射端新建会话会落在被投射设备的库里。
- **显示偏好存在投射端**：哪些项目显示属于投射端本地事务，不写回被投射设备。
- **凭据**：引用系统密钥文件路径，密钥本体不进投射端数据库；密码方式走凭据服务加密存储。
- **项目清单来源 = 并集**：被投射设备的「已登记项目」∪「实际有会话的项目」。实测两者不一致（登记 10 项、有会话 11 项），只取其一会让用户困惑。
- **归档会话排除**：投射的会话列表过滤掉已归档项。
- **断开后不缓存项目清单**：只保留设备条目。

### 已验证可用的能力（作为实现基础，不要重做）

- 投射端经 SSH 隧道挂载被投射设备的常驻会话主机（协议版本协商、一次性票据）。
- 读取被投射设备项目清单（其实测 10 项）。
- 读取/修改被投射设备设置（39 字段中 18 项可投射；写入-读回-回滚已验证）。
- 投射端新建会话落在被投射设备（实测对端会话数 +1）。

### 需要打通的链路（有明确未通过证据）

- **会话续接实际执行**：`resumeTask` + `subscribeConversationV4` + `sendPrompt` 调用链**全部被对端接受、无报错**，但被投射设备的会话库**没有新增消息**，会话状态也未变化。结论：调用被接受 ≠ 已执行，链路上有未打通环节（真实 UI 链路可能含额外的会话激活/绑定步骤）。这是本 spec 中风险最高的一项。
- **不选目录直接连**：当前连接流程把目录选择作为完成连接的必经步骤。

### 不变量（实现时必须保持）

- 投射端任务库中不得出现带远程前缀的索引行（当前为 0，需保持）。
- 被投射设备的项目列表不得因投射端的显示偏好而被修改。
- 投射端不得持有会话正文。

## Testing Decisions

**测试策略的核心约束：本项目的「电脑操作」是闭源占位包（永远返回不可用），因此没有 UI 自动化能力。** 可自动化的部分必须全部落在下面三层接缝上；纯 UI 表现只能人工确认。

什么算好测试：只验证**外部可观察行为**（查到什么、落到哪里、是否泄漏），不验证内部实现细节；跨机测试必须可重复自跑、且**不得污染用户数据**（只操作自己新建的一次性对象，改设置必须回滚）。

### 三层接缝（按成本从低到高）

1. **纯函数契约测试**（无需设备在线）
   - 领域：设置白名单筛选（哪些字段可投射、哪些必须排除）、显示偏好与来源标记的判定。
   - 先例：`packages/desktop/test/remoteSessionVisibility.test.ts`、`packages/ui/test/remoteScopeContract.test.ts`。

2. **跨机只读验证**（需被投射设备在线）
   - 领域：项目清单枚举与并集计算、会话列表（归档排除）、设备设置读取与白名单筛选。
   - 先例：`packages/desktop/test/e2e-remote-visibility.ts`、`packages/desktop/test/prototype-projection-scoped.ts`。

3. **跨机写验证**（需设备在线，带回滚/隔离）
   - 领域：新建会话落在被投射设备、远程登记项目、设备设置修改（写→读回→回滚）、会话续接（发出后必须能在对端观察到结果）。
   - 先例：`packages/desktop/test/acceptance-remote-device-settings.ts`（写入读回回滚）、`packages/desktop/test/e2e-remote-create-session.ts`（一次性测试会话）。
   - **硬性要求**：写测试只操作自己新建的一次性对象；改设置必须记录原值、读回确认、立即回滚；不得触碰用户的既有会话。

### 需人工确认的部分

- 侧边栏投射项目的视觉（图标/颜色区分、灰显状态）。
- 设备概览的布局与信息呈现。
- 连接/断开的界面反馈。

## Out of Scope

- **多设备同时连接**：首版只连一台。数据结构按列表存（将来增设备不需重构），但 UI 只暴露单台。
- **投射端持久化会话数据或索引**：明确不做，这是本 spec 的核心边界。
- **双向设置同步**：投射端的显示偏好不写回被投射设备；被投射设备的设置不自动同步回投射端。
- **侧边栏连接入口**：连接入口只在设置页。
- **会话内容全量预加载**：按需加载，不做全量拉取。
- **改动被投射设备的项目列表以外的设备数据**：投射端只能通过"登记项目"这一条路径改被投射设备（以及白名单内的设备设置）。

## Further Notes

### 这份 spec 的由来

此前两天的实现尝试反复返工，根因是需求在若干关键点上摇摆（会话是"同一份"还是"两份"、A 端存不存索引、断开后留什么、A 能否改 B 的数据）。经 Q1–Q19 逐条审问并全部确认后，上述决策已固化在 `CONTEXT.md` 的术语节里，本 spec 不再重新讨论这些取舍。

### 需要清理的既有痕迹

- 投射端任务库中的历史远程索引行已清理（当前 0 条），实现时需保持不引入新的。
- 之前的临时探针脚本（`packages/desktop/test/` 下的多个 `prototype-*`/`e2e-*`）中，验证手段有效的应保留为回归资产；一次性的应向验收脚本收敛，避免堆积。
