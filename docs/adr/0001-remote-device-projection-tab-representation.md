# ADR 0001：投射项目在投射端的承载形式

日期：2026-09-26
状态：已采纳

## 背景

远程设备投射要求「连接后，投射端的侧边栏出现被投射设备的项目」（见 CONTEXT.md「Projection」）。
但投射端侧边栏的项目列表由 tab 状态驱动（`projectWorkspaceTabs`）—— 一个项目要出现在
侧边栏，必须存在对应的 tab 条目。

这与另一条已确认的原则存在张力：「投射端只保留连接入口，不保存会话数据或索引」
（CONTEXT.md「Retained State」）。若为投射项目建立常规 tab，会引入投射端对远端项目
的持久化状态，且这些 tab 在断开后需要清理，容易留下不一致的残留。

## 决定

投射项目在投射端以 **transient tab**（瞬时投射条目）承载，而不是常规 workspace tab：

1. **不写入持久化的 workspace 历史**（`lastWorkspaceSession` 只保留设备条目，不保留投射项目）。
2. **不绑定工作目录**：投射条目代表"设备上的某个项目"，而非本机路径。
3. **生命周期严格跟随连接**：连接建立时按显示偏好创建，断开时全部移除；应用重启后不恢复
   （需重新连接才会出现）。
4. **会话数据仍实时从设备拉取**：投射条目本身不含会话内容或索引。

## 理由

- 满足「投射端不留存」：投射条目是内存态，断开即消失。
- 满足「侧边栏可见」：复用既有渲染路径，投射项可参与展开/折叠等交互。
- 避免持久化残留：不写历史意味着不存在"断开后残留的过期项目"这类状态。

## 被否决的方案

- **常规 workspace tab**：需写入持久化历史，并在断开/重连/异常退出时维护清理逻辑，
  状态一致性成本高，且违背"只保留连接入口"。
- **独立于 tab 的旁路列表**：需要在侧边栏新增一条并行渲染路径与交互（展开、选中、
  未读标记等全部重做），与既有项目的体验难以保持一致。

## 影响

- 投射条目与常规 tab 需要区分标记（渲染层按来源区分图标/颜色）。
- tab 的持久化与恢复路径必须显式跳过投射条目（已有先例：设备条目与远程 tab
  恢复路径已做跳过处理）。
- 应用重启后投射项目不自动恢复，用户需重新连接设备 —— 与「断开后不缓存项目清单」
  的既有决定一致。
