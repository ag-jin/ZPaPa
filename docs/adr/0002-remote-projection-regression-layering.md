# ADR 0002：远程设备投射的回归分层与测试目录纳入类型检查

日期：2026-09-27
状态：已采纳

## 背景

远程设备投射的开发期留下了 16 个验证脚本，散落在 `packages/desktop/test/`，
性质各异：有的是纯函数契约测试（`node --test`），有的是跨机验收（真实 SSH 到设备），
有的是探索期原型（一次性可行性验证），还有的会**写对端数据**。

三个具体问题：

1. **风险不分级**：会写对端设备的脚本与纯函数测试混在同一目录、同一命名习惯下，
   跑什么全凭记忆。写测试的失误代价是污染用户真实设备上的会话。
2. **`test/` 目录不在任何 tsconfig 里**：`e2e-remote-continue-session.ts` 引用了
   从未导入的 `createdSessionIds` 与 `assertTestOwnedTarget`，类型检查与 lint
   都报不出来（lint 只查语法与规则，不做名字绑定检查）。该脚本每次运行都会在
   **建完对端会话之后**才崩在护栏处 —— 既留垃圾又拿不到结论，长期无人察觉。
3. **一次性脚本越堆越多**：三个原型脚本的结论早已写进报告并被正式的验收脚本取代，
   但仍留在目录里，阅读者无法分辨哪个是当前有效的手段。

## 决定

### 1. 回归按「接缝层级」分三层，由单一入口驱动

`scripts/remote/regression.mjs`（npm: `pnpm remote:regression`）：

| 层  | 性质                       | 是否动对端数据             | 默认     |
| --- | -------------------------- | -------------------------- | -------- |
| 1   | 纯函数/契约，无设备无网络  | 否                         | 跑       |
| 2   | 跨机只读（真实设备数据面） | 否（只读）                 | 跑       |
| 3   | 跨机写带回滚               | **是**（仅自建一次性会话） | **不跑** |

层 3 默认不跑：是否动对端数据必须是调用方显式的选择（`--layer=3` / `--layer=all`），
而不是默认行为。跨机层在设备不可达时明确报错，不静默跳过 —— 跳过会让人误以为
"跨机验证通过"。

### 2. `test/` 目录纳入类型检查

新增 `packages/desktop/tsconfig.test.json` 与 `packages/ui/tsconfig.test.json`，
并入 `pnpm typecheck`。脚本仍由 `node --import tsx` 直接运行（不产出编译结果），
这两个工程只做类型检查（`noEmit`）。

ui 侧需要 `TSX_TSCONFIG_PATH=tsconfig.test.json` 才能让 tsx 解析 `@/*` 别名 ——
包内测试直接 import src，而别名只在 tsconfig 的 `paths` 里定义。

### 3. 探索期原型在结论落地后删除

原型脚本的结论一旦被正式验收脚本覆盖，即删除。保留它们的成本不是磁盘空间，
而是后来者必须逐个读代码才能分辨哪个手段当前有效。

### 4. 跨机写测试必须带隔离护栏

写对端数据的脚本一律使用 `test/support/testIsolation.ts`：

- 自建对象带 `zpapa-test-` 前缀（便于对端审计与事后清理）
- 写操作前经 `assertTestOwnedTarget` 校验目标是**本次运行创建**的
- 结束归档（不是删除：内容仍在，误判可恢复）

绝不按"最近活跃""状态为 completed""标题看起来像测试"这类启发式挑选目标 ——
那正是此前误改用户真实会话的原因。

## 理由

- **分层让风险变成显式选择**：读测试可以随手跑，写测试需要明确指定层级。
- **类型检查是最便宜的守门人**：未定义变量这类错误由 tsc 免费抓出，
  不必依赖"每次运行都完整跑一遍跨机脚本"这种昂贵且少见的检查。
- **删除过时原型降低认知负担**：目录里留下的应该是"当前有效的手段"，
  而不是"曾经想过什么"。历史在 git 与报告文档里。

## 被否决的方案

- **引入测试框架（vitest 等）统一调度**：本仓当前没有测试框架，`node --test` +
  `node --import tsx` 已能满足（含跨机脚本需要真实网络与 SSH 的场景）。
  引入框架会把"跨机验收"这类非常规测试挤进框架的假设里，收益不抵改造面。
- **把写测试从仓库里移除，只留只读**：写路径恰恰是最容易出错、最需要回归的部分
  （实测已发生两次污染）。正确做法是隔离 + 分层，而不是放弃覆盖。
- **让 lint 覆盖未定义变量**：oxlint 不做跨文件名字绑定检查，这是类型检查的职责；
  已在 tsc 层面解决，不重复造轮子。

## 影响

- 新增/修改跨机脚本时，按层级登记到 `scripts/remote/regression.mjs` 的 `SUITES`。
- `pnpm typecheck` 现在也会检查两个 `test/` 目录；新增测试文件即被纳入。
- 写测试的运行方式固定为 `--layer=3`，其存在本身即"会动对端数据"的提示。
