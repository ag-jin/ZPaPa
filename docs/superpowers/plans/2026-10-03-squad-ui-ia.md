> 依据：用户 2026-10-03 的设想（首页插件市场下 = **智能体/小队的配置入口**；要吸收 multica 的 UI；**项目下**增加**小队/单智能体窗口**）
> + 规格 §11（IA 与设计系统）+ multica README 的实际界面清单（本轮取回，见第三节）。
> 这份是**提案**；标 **【待你拍板】** 的地方留给你。

## 一、一句话：三个面，各承接一件事，**不重复**

| 面 | 落在哪（用现有壳） | 承接什么 |
|---|---|---|
| **配置入口** | **首页草稿区**：`packages/ui/src/app-shell/WorkspaceShellLayout.tsx` 的 `draftComposerHeader`，紧接 `WorkspacePluginPreview` 之下（**不绑 `isOfficeMode`**） | **智能体 / 小队的定义**：列表 + 新建 + 编辑（队长、成员、8 槽位指令）+ 启停 / 归档 |
| **项目下的「小队窗口」** | **项目作用域的一个窗口**（与会话窗口同级；**不是**全局顶层导航） | **运行的一切**：工作项看板（父项批次 → 子项）、**审查（通过 / 打回）**、**放弃整批**、**活动时间线**（§11.2 自建）、唤醒规则入口 |
| **会话里的穿透点** | 会话窗口的「智能体」入口（头像簇 + 「N 在跑」） | 从会话直达正在跑的 run；**点某次 run ⇒ 打开它的独立会话**（§11.1 决策 C11 的合并入口） |

**数据真源只有一处**：智能体 / 小队的定义在服务层（文件 + 台账）。上面三面都只是**视图**，
不各存一份 —— 否则就是「同一语义两处实现」，迟早在「谁改了谁没改」上分叉且不报错。

## 二、为什么这么分（逆推用户的两句话）

- 「首页插件市场下 = **配置**入口」⇒ 那是**定义面**：静态、低频、跨项目都可用（一支小队不绑定某个项目）。
- 「**项目下**增加小队/单智能体窗口」⇒ 那是**运行面**：运行天然有项目归属（工作树、分支、工作项都在某个仓库里）。
  ⇒ **定义 / 运行 分家**，各自落在自己该在的层级：定义在首页（无项目上下文也能改），运行在项目窗口（必须有仓库）。
- 这与规格 §11.1「**名册在设置、运行在会话**」的**精神**一致（定义与运行分开），但**落点变了**：
  名册从「设置 ▸ 实验功能」**搬到首页**（你的设想）。⇒ **口径变更要登记进 spec §17**（免得下一个人拿 §11.1 字面来对账）。

## 三、从 multica 吸收什么（按它的实际界面逐条对，不空谈）

multica README 的界面清单（本轮实取）：**issue 板**（agent 像同事一样出现在板上、可被指派）、
侧栏 **Agents** / **Runtimes**、**Squads**（队长分派）、**Execution log**（回放每次工具调用/命令/报错，带时间戳）、
**Steering**（运行中回话，消息落进当前 run）、**Usage analytics**（每次 run 的花费）、**Review gates**（成果进 review 不进 main）、
**Inbox**（agent 需要人拍板时才 ping）、**Autopilots**（cron）、**Chat**、**Projects**。

| multica 的面 | 我们吸收成什么 | 归谁 |
|---|---|---|
| issue 板：agent 是被指派人 | **工作项看板**：卡片 = 工作项，卡上出现**队员头像**（九色板）+ 状态 | 项目窗口 |
| Squads（队长分派） | 已有（队长 run + 派单） | 服务层 ✓，窗口里呈现 |
| Execution log（回放工具调用） | **不新造日志视图**：点某次 run ⇒ **打开它的独立会话**（会话本就逐条有工具块与时间戳） | 会话（复用） |
| Steering（运行中回话） | 天然具备：我们的 run 就是会话 ⇒ 直接发消息 | 会话（复用） |
| Review gates | **审查（通过/打回）** 按钮 | 已有服务面，搬进项目窗口 |
| Inbox | 我们的 `InboxItem`（已定稿：`kind` + 严重级 + 已读/归档） | **落点见第六节（待你拍板）** |
| Autopilots | 现有 cron 自动化 + **唤醒规则**（WakeRule）入口 | 项目窗口的「规则」子页 |
| Usage analytics | §11.4 的可观测（队长每次 run 的**派单数 / 合并结果 / 防失控触发**记为活动事件）；**成本记账属 P3** | 时间线事件 |
| Agents 侧栏（建 agent：名字/提供商/runtime） | **首页配置入口**（我们的「协作智能体」= 名字 + 系统提示 + 记忆范围 + 模型） | 首页 |
| Chat / Projects | 已有（会话 / 工作区） | ✓ |

**明确不吸收**：multica 的 **Runtimes（计算机/daemon 管理）**——我们不做多设备联动（已定口径）；
它的**重平台**部分（Go + Postgres + daemon spawn 26 种 CLI）——见记忆里的既有判定。

**「可视化」的分工要说清**：multica README 里**没有**明确的时间线视图；
**活动的可视化是我们自建**（§11.2 决策 C1 已定：lane = 队员 / station = 一次运行 / 弧线 = 交接，
**不复用** workflow 时间线组件，只沿用九色板与语义状态色）。所以「吸收 multica」= 吸收**面与范式**（板 + agent 即被指派人 + run 详情复用会话 + review gate + inbox + autopilot），**不是**吸收像素。

## 四、落点（技术）

- **首页配置入口**：`WorkspaceShellLayout.tsx` 的 `draftComposerHeader` 内、`WorkspacePluginPreview` 之后。
  复用现有 `SquadEntryLists`（列表）与 `SquadCreateDialogs`（三个新建表单）——
  即**把现在设置页那半「配置」搬过来**，不是重写。
- **项目窗口**：项目作用域的一个窗口/标签（与会话窗口同级）。承载看板 + 审查 + 放弃 + 时间线 + 规则。
- **设置 ▸ 实验功能**：**只留总开关** + 一行指引（「配置入口在首页；运行在项目窗口」）——
  避免「设置页也有一份」的第三份拷贝（本轮修的那个「入口被错误态连坐藏掉」的卡片，随搬家退役）。
- **设计系统**：字号 `text-ui-*`、圆角按层级、语义色 token、复用 `components/ui/` 原语（§11.3）；文案进两语（§11.4）。

## 五、顺序（我按此推进；每一步都能单独验收）

1. **首页配置入口**（最小、马上可用）：解锁「建队长 + 建队员 + 建小队」。
2. **项目窗口的看板 + 审查/放弃**（运行闭环可见）。
3. **时间线可视化**（§11.2 自建，最贵，放最后）。
4. **Inbox**（落点见第六节）。

## 六、要你拍板的一件事

**Inbox 落哪？** 你先前答「首页插件市场下面」，但那一处现在定位成**配置入口**了（定义面）。
我的建议：**Inbox 落「项目窗口」**——它是「运行中需要人介入」的面，与看板/审查同族；
首页那处只放**配置**（定义面）。这样「定义 / 运行」这条分界线不会被一条通知面打破。
