# 多智能体小队 P2c：Inbox 落地计划（**待用户过目**）

> 口径：这份是**提案**，不是已定的规格。凡标 **【待你拍板】** 的地方都留给你；未拍板前我不动手写实现。
> 依据：`docs/superpowers/specs/2026-10-01-multi-agent-squad-design.md`；现状由本轮只读侦察给出（下文第三节）。
> 验收方法按你的口径：**逆推 + 穷举**两法并用，**只有逆推视为未完成**。

## 一、目标（一句话）

把规格里已经承诺、却在 P2b 被推迟的那条链做成**用户可达**的：
**「需要人介入的事」产生 → 落成一条可查的 InboxItem → 在界面上看得见 → 能标已读/归档。**

P2b 里它的机械形态只有一条：`blocked` 状态变迁（冲突解不了时）。**「进 Inbox」这一步从来没有实体。**

## 二、逆推：从规格原文反查「因此必须为真什么」

| 规格原句（出处） | 反推出的要求 | 现状 |
|---|---|---|
| `InboxItem`：**类型 + 严重级**（`action_required` / `attention` / `info`）；**已读 / 归档**（§3.x 实体表） | ① 要有**实体与表**（迁移追加）② 严重级是**枚举**，不是自由文本 ③ 已读与归档是**两件事**（可读未归档 / 已归档） | ❌ 只有事件名 |
| `blocked` = 卡住、需人或其他 agent 介入（**联动 Inbox**）（§4.x） | `blocked` 的**产生点**必须同时产出一条 InboxItem（否则「联动」是空话） | ❌ `blocked` 只改状态 |
| 合并冲突解不了 → 置 `blocked` + **进 Inbox**（§5.7.4 / §16 S-E13） | 冲突这条路径要有 InboxItem，且**说清是哪一批 / 哪两个分支** | ❌ 无 |
| 队员失败 → **留分支** + 进 Inbox + 标 `blocked`（§6.2 一带） | 失败路径同样要进 Inbox（**且分支必须留着** —— 与「产出活到合并」不冲突） | ⚠️ 有 `failMemberRun` 出口，无 Inbox |
| 看门狗：把「进行中但宿主已消失」的 run 标 `error` **并入 Inbox**（§6.6 / §16 S-C4） | 启动和解/看门狗这条路径也要进 Inbox（**这正是第 16 轮那条启动和解**该有的可见归宿） | ❌ 无面板 / 无 `error` 状态？**【待你拍板】** |
| 「需人决策时停下 → 进 Inbox」（§5.x 流程） | 需要一条**通用入口**（不是每种情况各写一份） | ❌ 无 |
| 「渠道创建 / 触发工作项：渠道只到对话 —— **但 Inbox 通知可以推送到渠道（只读）**；『不派活』≠『不通知』」（§2.x） | 渠道推送**属 P3**（见「明确不做」表里的第 10 项） | 不适用（P3） |
| 「订阅者 + Inbox（**完整语义**）」被列进「本阶段不做 / 后续」与 P3（§1 表第 10 行、§13 表） | **订阅者**不在本次；本次只做**单机单用户的 Inbox** | 不适用 |

**逆推暴露的一条关键耦合**：`blocked` 现在是**冲突**的机械形态，而 §16 里还有「失败 → 留分支 + Inbox + blocked」。
**同一状态 `blocked` 承担两种语义**（等人在 Inbox 处理 / 等人解冲突）⇒ InboxItem 的类型字段必须能把它们分开，
否则「联动」会退化成「都是 blocked」（**这正是 2026-10-02 第 1 轮裁定过的「两类 run 长得一样」同型缺陷**）。

## 三、现状（只读侦察结论，2026-10-03）

- **事件**：`DispatchEvent` 有 `inbox.notified{ workItemId, reason }`，**唯一产生者**是 `planDispatch`
  的四条 skip 路径（指派给人 / 小队不存在 / 已归档 / 已停用）；**消费方只有 host 的一行日志**。
- **状态**：`blocked` 已存在，由 `advanceAfterChildrenDone` 在**冲突**时写入（逐队员冲突 / 整批合回冲突两条）。
- **失败出口**：`failMemberRun`（把失败 run 移出活跃集）；启动和解（第 16 轮）也在用同一出口。
- **无**：InboxItem 实体 / 表 / 迁移 / 服务读写 / 任何界面。
- **IA 现状**：小队的最小视图落在**设置页**（spec §17 已登记「运行记录落在设置页与 §11.1『名册在设置、运行在会话』冲突」）。

## 四、设计草案（**每处都要你点头**）

1. **实体与表**【待你拍板 ①②③】
   - `inbox_items(id, workspace_key, workspace_path, kind, severity, title, detail_json, work_item_id?, run_id?, created_at, read_at?, archived_at?)`
     —— `kind` 回答「**这是什么**」（`merge_conflict` / `member_failed` / `run_orphaned` / `dispatch_skipped`），
     `severity` 只回答「**要多急**」（`action_required` / `attention` / `info`）。
   - 迁移编号：**0007**（0006 是 `squad_runs`；0004/0005 已被 `work_items` / `wake_rules` 占用）。
   - **去重/幂等**：同一事实重投（同 `eventKey`）**不得**产生第二条（沿用「幂等键的稳定一半」这条既有纪律）。
2. **写入口（唯一写者）**【待你拍板 ④】
   - 服务面 `recordInboxItem(...)`（**只登记**）＋ `markRead` / `archive`（**只改这两列**）。
   - 产生点先接**已有的四个真实场景**（不发明新场景）：冲突 → blocked、队员失败、启动和解的残留 run、`planDispatch` 的四条 skip。
3. **消费面（先做「看得见」）**【待你拍板 ⑤】
   - **最小可见**：设置页的实验分区里加一个 Inbox 列表（与小队最小视图同一处），列出未归档项，可标已读/归档。
   - **与 §11.1 的冲突**：规格说「运行在会话」。**本次先放设置页**（与既有最小视图同处，成本最低），
     并把这次偏离**再登记进 §17**（口径：P2c 的 Inbox 先随最小视图落位，会话内联视图留 P3）。
4. **不碰的东西**：`blocked` 状态本身、冲突判定、工作树/分支生命周期 —— 本次只**新增**「记录 + 看见」。

## 五、穷举：验收格（先列全集，再逐格给结论）

**维度**：产生者(4) × 严重级(3) × 消费动作(3) × 失败态(3)。

| 格 | 期望 | 谁来验 |
|---|---|---|
| 冲突 ⇒ `merge_conflict` / `action_required` | 一条、带 workItemId 与分支名 | 服务层用例（真实编排器） |
| 队员失败 ⇒ `member_failed` / `attention`，**且分支仍在** | 一条、分支未被删 | 服务层用例 |
| 启动和解 ⇒ `run_orphaned` / `attention` | 一条（**这是第 16 轮那条和解应有的可见归宿**） | 服务层用例 |
| 四条 skip 各 ⇒ `dispatch_skipped` / `info` | 各一条，reason 原文可读 | `planDispatch` 用例扩展 |
| 同一事实重投 | **不产生第二条** | 幂等用例（变异：去掉去重 ⇒ 必红） |
| 已读 / 归档 | 只改对应列；已归档不再出现在默认列表 | 服务层用例 |
| 严重级三态 | 三格都能显示，且**不靠文案**判（是枚举） | 类型 + 用例 |
| 归档后被重投 | **不复活**（或复活成新的一条？**【待你拍板 ⑥】**） | 用例 |
| 无 Inbox 服务 / 库未就绪 | **skip 但留痕**（不静默） | 接线守卫 |

## 六、明确不做（本次）

订阅者与订阅分发、渠道推送、评论 / 活动时间线、PR 集成、成本记账、AI 建 agent 向导、run 看门狗（**并入 Inbox 这件事只做「启动和解」那一格**）、Inbox 的会话内联视图。
