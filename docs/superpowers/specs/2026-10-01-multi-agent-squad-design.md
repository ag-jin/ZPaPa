# 多智能体小队（Multica 借鉴）设计规格

- **状态**：设计定稿（spec），待实现
- **日期**：2026-10-01
- **来源**：`docs/multica-squad-absorption-review.md`（调研 + 可行性核验 + 冲突抉择的完整过程记录）
- **决策依据**：本规格所有决策均已与用户逐条确认；凡引用「决策 X」处可在评审文档对应小节查到理由。

---

## 1. 背景与目标

**动机（用户原话的意思）**：**用多个 agent 交叉验证，即使同一个模型，也比单 agent 更容易发现问题。** squad、排班、互通都只是手段。

**目标**：在 ZPaPa 中新增一套**协作编排机制**，让用户能：

1. 定义**协作智能体**（独立实体，各配信息与模型）；
2. 组**小队**（队长 + 队员），由队长协调；
3. 把**工作项**（含父子树）指派给个人或小队，**自动一轮轮推进**；
4. 队员执行时各自用**独立工作树**，审查通过后合并、合并后抛弃；
5. 全程在**会话窗口**里可见、可控、可叫停。

**性质**：**实验功能**——另起一套机制、与旧功能并存、可整块关掉，**不替换**现有 subagent / automation。

## 3. 核心概念与实体

### 3.1 分层关系

```
小队（Squad）              ← 一层协调：队长协调 · 讨论 · 工作树隔离 · 审查后合并
──────────────────────────────────────────────────────────
项目下的智能体会话         ← 底座：不管在不在小队里，都挂在项目/工作项下的独立会话
──────────────────────────────────────────────────────────
自有 CLI 会话运行时         ← 执行体：父 = 项目 / 工作项
```

**沟通面 ≠ 执行面**（决策 C6）：共享沟通会话只用于讨论 / 汇报 / 队长协调；**队员的执行发生在各自的独立运行 + 工作树里**，不在会话中执行。

### 3.2 TeamAgent（协作智能体）

一等独立实体，**自成一份定义**，与现有 subagent 完全分开（决策 C3 三重隔离）。

| 字段 | 说明 |
|---|---|
| `id` | **稳定 id**（记忆 key 用它，不用名字） |
| `name` / `description` / `color` | 身份；`color` 取自 `SUBAGENT_COLORS` 调色板（**共 8 色**：yellow/red/orange/green/cyan/blue/purple/pink；按实例序号分配，**不编码状态**） |
| `systemPrompt` / `instructions` | 行为 |
| `skills[]` | 技能，多对多挂载，可逐个禁用 |
| `modelSelection` | 复用 `ModelSelection`（providerId / modelId / reasoningLevel）——**每个智能体可用不同模型** |
| `tools[]` / `disallowedTools[]` | 工具集 |
| `permissionMode` | `auto` / `plan` |
| `memoryScope` | `user` / `project` / `local`（复用现成能力） |
| `enabled` | 启用开关 |
| `provenance?` | 若从现有 agent **预填**而来，记来源；**此后无持续引用** |

**存储**：实验命名空间，与现有 subagent 目录分离，可整块删除。
**定义来源**：新建时可从现有 agent **一键预填一次**，预填后各自独立（对齐 Multica：agent 本就是独立记录，无复制/引用概念）。
**不绑 host**（决策 E）：单机运行，不需要 `hostBinding` 字段。

### 3.3 Squad（小队）

| 字段 | 说明 |
|---|---|
| `id` / `name` / `description` | 身份 |
| `leaderAgentId` | 队长，必须是一个 TeamAgent |
| `members[{ agentId, role? }]` | 队员；leader 自动作为成员 |
| `instructions` | 队长指令（8 槽位，见 §5.4） |
| `enabled` / `archivedAt?` | 状态 |

**指派语义**：工作项的 `assignee` 可为 `user | agent | squad`。指派给 squad 时，解析出 `leaderAgentId`，为该队长排一次**队长角色 run**（打 `is_leader_task` + `squad_id` 标记），并注入队长简报。

**队长简报（`SquadBriefing`）由三段构成**（2026-10-01 定；P1 曾只落两段，`protocol` 缺失）：

| 段 | 来源 | 内容 |
|---|---|---|
| `roster` | 系统生成 | 花名册：队长与队员、各自角色与能力 |
| `protocol` | **系统生成（非用户可写）** | **操作协议**：三道闸（`max_fires` / `rate` / `loop`）与判定次序、`stopCondition` 与 `maxRounds` 语义、派单只产出子项与派发事件**不改父项状态**、**串行**合并到集成分支、**整批通过才合回主分支**、冲突解不了 → `blocked` + 进 Inbox、审查未通过前工作树**存活**、合并后才抛弃 |
| `instructions` | 用户填写 | 8 槽位，见 §5.4 |

**为什么 `protocol` 必须独立、不得并入 `instructions`**：它恰是「**机制**」那一半，而 `instructions` 是用户意图那一半。并进去等于把机制交还给用户去写——用户没写就等于**队长不知道规则却照跑**，且**不报错**。这正是「看起来没问题」的形态。（合于「我们只提供机制，怎么用由用户定」。）

### 3.4 WorkItem（工作项）

| 字段 | 说明 |
|---|---|
| `id` / `workspaceIdentity` / `workspacePath` | 键遵从 `workspaceIdentity?.trim() \|\| workspacePath`（决策 C14） |
| `parentId?` | **完整父子树**：任意深度 |
| `stage?` | 分阶段（`stage:N` / `each_stage`） |
| `title` / `body` | 内容 |
| `status` | 生命周期，见 §4 |
| `assignee` | `{ type: user \| agent \| squad, id }` |
| `labels[]` / `properties{}` | 元数据（labels + 带类型的自定义属性） |
| `position` | 手工排序 |
| `deliverables[]` | 交付物引用，见 §9 |
| `pullRequests[]` | PR 关联，见 §9 |
| `archivedAt?` | 归档 |

### 3.5 WakeRule（唤醒规则）

| 字段 | 说明 |
|---|---|
| `id` / `workItemId` | 挂在**工作项**上 |
| `kind` | `event` / `at` / `every` / `cron` |
| `mode` | `once` / `continuous` |
| `condition?` | `issue_field` / `children_done` / `pull_request` / `other_issue` |
| `filters?` | 事件过滤器 |
| `nextFireAt` / `intervalSeconds` / `cronExpression` / `timezone` | 调度字段 |
| `maxFires` / `fireCount` / `pausedReason?` | 防失控 |
| `expiresAt?` / `onTimeout?` | 过期与超时行为 |

### 3.6 Run（一次运行）

| 字段 | 说明 |
|---|---|
| `id` / `workItemId` / `agentId` / `sessionId` | 归属 |
| `isLeaderTask` / `squadId?` | 队长角色 run 标记 |
| `worktree?` | 本次运行的工作树（若开启隔离） |
| `status` | **执行态**（`running` / `completed` / `error`）——**内部，不外露**（§4） |
| `usage` | per-run 成本 / token 记账 |
| `watchdog` | 超时 / 重试 / 熔断状态 |

### 3.7 其他实体

- **Subscriber**：`(workItemId, 主体, reason)`，reason ∈ creator / assignee / commenter / mentioned / manual / delegated；含 `optOutScope`（issue / subtree）与 tombstone 行。
- **InboxItem**：类型 + 严重级（`action_required` / `attention` / `info`）；已读 / 归档。
- **Comment / Activity**：工作项下的评论与事件流。
- **Deliverable**：工作项产出物（计划 / 文档 / 实现 / diff / 预览 / 测试结果）。

### 3.8 持久化与存储归属

| 数据 | 存放 |
|---|---|
| 工作项 / 小队 / TeamAgent / WakeRule / Subscriber / InboxItem / Comment / Activity / Deliverable / Run 记录 | `packages/services/src/session/tasksDatabase`（现有 SQLite）**新增表**，通过新迁移追加 |
| TeamAgent / Squad 的**定义文件** | 实验命名空间（如 `<ws>/.zcode/squad/`），可整块删除 |
| **记忆** | 沿用 `agent-memory/<稳定 id>` |
| **工作树** | `<repoRoot>/.worktree/`，git 元数据由 git 自身管理 |

**约束**：
- 工作项**不是** task 的别名；**不改** task 表语义（C7 要求工作项排除在自动归档之外）。
- 迁移**只追加**（新增表 / 列），不重命名或删除既有列。
- 关闭实验后**表保留、不再写入**，数据不丢。

### 3.9 接口、事件与错误码

- **服务层**：新增独立服务（如 `packages/services/src/squad/`），为唯一入口；**UI 不直接访问 Repo**。
- **协议**：新增 / 扩展走 `packages/shared/src/zcode-protocol-v4/`，**必须**带运行时校验（AGENTS.md）。
- **统一派发事件形状**：`workitem.assigned` · `workitem.status_changed` · `workitem.child_completed` · `wake.rule_fired` · `run.completed|failed|cancelled` · `squad.member_changed` · `worktree.merged`。
- **错误 / 结果码**（skip 与 fail 必须分开，对齐 Multica）：
  - `dispatch_skipped`：对象已归档 / 无可用运行时 / 离线 —— **非失败**，不进失败率
  - `dispatch_failed`：真实错误
  - `wake_paused`：附 `reason ∈ {max_fires, loop, rate}`
  - `merge_conflict`、`worktree_orphan_reclaimed`
- **幂等键**：派发事件携带 `(workItemId, ruleId, revision, eventKey)`；重试必须可安全重放。

### 3.10 生命周期细节、边界与限额

- **删除 vs 归档**：智能体 / 小队**只归档不硬删**；工作项可归档；评论 / 活动**只增不改**。
- **小队成员变更**：**不影响**已派发且进行中的 run；新派发按新花名册。
- **唤醒规则编辑**：每次实质编辑 **`revision` +1**；过期 revision 的进行中派发**自动作废**（fencing）。
- **限额（默认值，实验分区可调）**：树深 ≤ 5 · 单工作项子项 ≤ 50 · 单工作项并发 run ≤ 8 · 单小队并行队员 ≤ 6 · 队长单轮最多派 10 个子项。
- **取消**：用户可取消任意进行中的 run；取消后其 worktree 按状态处理（未合并 → 回收）。

---

### 3.11 数据保留与清理

| 数据 | 保留策略 |
|---|---|
| 评论 / 活动 / 沟通记录 | **只增不改**，默认永久保留（本地） |
| Run 记录与成本记账 | 保留；保留期可在实验分区配置 |
| 工作树 / 分支 | 合并即删（§6.3）；孤儿启动回收（§6.6） |
| **关闭实验** | **不删除任何数据**——表保留、可手动清理 |

原则：**实验关闭是「停止使用」，不是「销毁数据」**。任何自动清理都要能在实验分区里看到并关闭。

## 4. 生命周期与状态

### 4.1 工作项生命周期（4 category / 6 键）

| category | 键 | 含义 |
|---|---|---|
| unstarted | `todo` | 未开始 |
| started | `in_progress` / `in_review` / `blocked` | 进行中 |
| done | `done` | 终态之一 |
| closed | `cancelled` | 终态之一 |

**机器只读 category**（判终态、算 `children_done`）；键只作标签。**聚合判定一律用 category，不用键名。**

规则：
- `in_review` = 交付后未验收的独立停留点（多 agent 互查的落点）。
- `blocked` = 卡住、需人或其他 agent 介入（联动 Inbox）。
- **`completed`（run 结束）≠ `done`（工作完成）≠ `closed`（归档）**，三层分开。

### 4.2 状态只描述生命周期，不驱动执行

**「进入 `in_review`」不自动调用审查 agent。** 何时唤醒谁由**唤醒规则 / 条件**决定。状态只提供**槽位**。

### 4.3 四套状态的所有权（决策 C2）

| 状态 | 所有者 | 可见性 |
|---|---|---|
| 工作项生命周期 | **工作项服务（唯一写者）** | **对外**（产品级） |
| 执行态（run） | CLI runtime | 内部 |
| 派发态（dispatch） | 调度器 | 内部 |
| automation 生命周期态 | automation | 内部 |

**用户 / agent / 调度器 / 队长都只能发「派发事件」**，由工作项服务消费后流转。禁止任何一方直写工作项状态。

## 5. 触发与编排

### 5.1 三路输入、一处写入

| 来源 | 形态 |
|---|---|
| **用户** | 指派负责人 / 派给整个小队 / `@` 智能体起一次运行 |
| **队长** | leader-role run 里派单：显式 @队员、或建子工作项 |
| **规则 · 排班** | 条件满足（`children_done` 等）或 cron 到点 |

三路都**不直接改状态**，只发**同一形状的派发事件**。

### 5.2 三处易丢的语义

1. **`@` ≠ 指派**：触发一次运行，**不改**负责人与状态。
2. **防失控只约束非人发起**：`max_fires` / `loop` / `rate` 只对规则型生效；**用户手动「现在就跑」豁免**。
3. **终止条件写进指令**：系统不判断「计划已完成」。

### 5.3 自动推进链条（一轮一轮，不是一次性批处理）

```
你建计划 + 指定队长
  → 指派事件唤醒队长一次（队长角色 run，带简报）
  → 队长拆解 + 派单（建子工作项 / @队员）
  → 队员并行执行（各自独立会话 + 工作树）
  → 子项全完成（children_done）→ 再唤醒队长  ⟲ 回到派单
  → 需人决策时停下 → 进 Inbox
```

### 5.4 队长指令模板（落在 `Squad.instructions`，可按工作项覆盖）

| 槽位 | 必填 | 作用 |
|---|---|---|
| 目标 | | 这个计划成功长什么样 |
| 拆解规则 | | 怎么拆成子工作项：粒度与判据 |
| 派单规则 | | 派给谁、能否并行 |
| 独立性要求 | | 队员执行时不得互相看结论（四红线之②） |
| 验收标准 | | 每个子项怎样算过 |
| **收手条件** | **必填** | 何时继续 / 收工 / 叫人 |
| 汇报格式 | | 向人汇报什么、何时进 Inbox |
| **轮次上限** | **必填** | 最多派几轮（与 `maxFires` 呼应） |

写含糊的结果只有两种：**早早停了等人催**，或**没完没了地派直到撞上 `maxFires`**。

### 5.5 防失控（硬规则，不靠 prompt）

| 规则 | 阈值 / 行为 |
|---|---|
| `maxFires` | 连续规则默认上限 **20**（1–1000）；达上限那次仍是合法 run |
| `rate` | 一小时内 run 次数 **≥ 12** → 暂停，`pausedReason=rate` |
| `loop` | run 链中同一规则出现 **≥ 2** 次 → 暂停 |
| `merge` | 同工作项重复触发**合并成一次 run**（唯一键 `(ruleId, revision, eventKey)`） |
| 自我承认短路 | 输入全来自目标 agent 自身 → 只消费，不启动新 run |

**判定次序（实现契约）**：先判三道闸（`max_fires` → `rate` → `loop`），再判去重，去重内**先 `acknowledged` 后 `merged`**。**人发起（`manual`）只豁免三道闸，不豁免去重**——去重是「同一事实只处理一次」，与谁发起无关。

### 5.6 automation 与唤醒规则的分工（决策 C5）

- **automation**：管「**无工作项**的定时任务」（保留原样）。
- **唤醒规则**：管「**挂在工作项上**的 event / 条件」。
- automation 若要指向工作项 → **走唤醒规则**，不另开一路。

---

### 5.7 关键时序与幂等

1. **指派幂等**：同一 `(workItemId, assignee, assigneeVersion)` 重复指派**只唤醒一次**；队长 run 进行中时的重复指派**合并**为同一次（不排队堆积）。
2. **队长唤醒与派单的边界**：队长 run 只产出**派发事件与子工作项**，**不改父项状态**；父项状态由工作项服务按条件推进。
3. **`children_done` 判定**：子项**全部** `category ∈ {done, closed}` 才触发；**用 category，不用键名**。
4. **合并时序**：**串行**合并；集成分支上的冲突由**队长 run** 解决，解不了 → 置 `blocked` + 进 Inbox；**整批通过后才合主分支**。
5. **状态推进幂等**：每次流转携带期望前置状态（**CAS**）；不匹配则丢弃并记事件，**不报错**。
6. **关闭实验开关**：停止**新**派发；**不中断**进行中的 run；入口隐藏、数据保留。

#### 5.7.1 `eventKey` 构造规则（接线前必须闭合；2026-10-01 已定）

§3.9 注入的幂等键是 `(workItemId, ruleId, revision, eventKey)`，而 `eventKey` **如何构造**此前一直未定义。这是最危险的一类留白：不定义，接线方会就地拼串，**重复投递的事件会静默重复触发**——不报错、看起来正常。

**唯一构造器**：`computeEventKey(rule, fact)`，随域模型一起从 `shared` 导出。调度器与 Repo **都调它**，**不得各自拼串**。

**两个族，前缀不同**（于是「事件触发的第 N 次」与「排期的第 N 次」永不撞键）：

**(A) 事件族（`kind: "event"`）**：`eventKey = "e:" + identity`，`identity` 按**优先级**取第一条可用者：

1. `"id:" + source + ":" + externalId` —— 事件自带的**稳定 id**（如 GitHub `X-GitHub-Delivery`、`event.id`）。**首选**。
2. `"fp:" + source + ":" + eventType + ":" + sha256(stableStringify(payload))` —— 无稳定 id 时，退用**完整 payload 的规范化指纹**。

- **既无 id、payload 又不可规范化 → 抛**（不 fire）。不可去重的事件每次重投都会重复触发且**不报错**，属「看起来没问题」形态，必须响亮失败。
- 指纹用**完整 payload**（不是 `filters` 子集）：唯其如此，两个**仅时间戳不同**的事件才会算出不同 key。
- `stableStringify` 必须钉死：对象键按码点升序、数组保序、数字最简形式、字符串 JSON 转义；并排除**易变字段**（`deliveryAttempt`、投递时刻等）。**易变字段清单是同处声明的常量**，不得在调用点就地过滤。

**(B) 排期族（`at` | `every` | `cron`）**：`eventKey = "t:" + scheduledFor`，`scheduledFor` 是本次**应当触发的名义时刻**（epoch ms 整数），**不是**调度器发现它的墙钟时刻。

- 重启后重算 `nextFireAt`（§6.6 第 3 项「漏掉的周期合并成一次」）、misfire 补发、同一次名义时刻被 tick 反复捞到——三种情形都必须算出**同一个 key**，去重才成立。
- 名义时刻必须落在**调度网格**上，因而**确定**、不依赖运行时刻：`at` 即 `at` 本身；`every` 由 `intervalSeconds` 与一个**钉死的 epoch 锚点**对齐；`cron` 由表达式与 `timezone` 定义。**锚点必须写进契约**（否则重启后换锚点，同一格算出不同 key，去重失效且静默）。

**`filters` / `eventTypes` 不参与 `eventKey`。** 它们判「**是否匹配**」，不判「**是哪一个**」。把 `filters` 拼进 key，会让规则作者改一下过滤器就换掉一把去重键 → **历史去重记录全部失效**（同一事实被重新处理一次）。**这是本条最重要的一句。**

**与 `revision` 的关系**：`eventKey` 里**不含** `revision`（它已是四元组的独立一项）。规则被编辑 → `revision` 变 → 四元组整体变 → 历史去重**刻意不复用**（规则换了口径，同一事件值得再处理一次）。

**与去重三元组的关系**：§5.5 的去重键是 `(ruleId, revision, eventKey)`，**不含 `workItemId`**——去重按**规则**维度；同一 `ruleId` 不跨工作项，故二者等价。但**落痕时四元组仍带 `workItemId`**（可读性与按工作项审计）。

## 6. 隔离与执行

### 6.1 工作树（每次运行的选项）

「是否开工作树」是**本次运行**的属性，不是小队专属：

- **小队队员**：执行期建独立工作树 → 审查 → 合并 → **抛弃**。
- **单独安排的智能体**：直接在工作区改，**没有合并那一步**（也就没有工作树 / 孤儿问题）。

### 6.2 生命周期

```
派单 → 建 worktree（派生独立分支）→ 执行 → 讨论/审查
     → 队长合并到集成分支 → 整批过了再合回主分支 → 删工作树 + 删分支
```

**准确规则**：worktree 活到「该队员这次工作**被合并**为止」——**审查被拒时必须存活到合并**，不能提前删。

**⚠️ 接线契约（本层库不做，由调用方保证）**：回收器 `reap` 的「活跃」判据**完全由入参 `activeBranches` 决定**。该入参**必须包含所有未合并的队员分支——包括被打回待修复的**；回收只针对**已合并 / 已放弃**的。若接线方用「当前有没有在跑的 run」当口径，被打回待修的队员工作树会在**下次启动被静默回收**（上面那条「审查被拒必须存活」就落空了），且回收过程**不报错**。（2026-10-01 P2a 整支终审发现；已同步登记进 §17 表。）

### 6.3 合并（决策 A / B）

- **目标**：**集成分支 `squad/integration/<工作项>`**；整批过了再一次性合回主分支（主分支干净、整批可整体放弃）。
- **⚠️ 分支命名必须避开 git 的 D/F 冲突**（P2a 实测发现，2026-10-01）：git 分支是文件系统 ref，**`squad/<工作项>` 与 `squad/<工作项>/<队员>` 不可能共存**（前者是文件、后者要求它是目录）。故两个命名空间**从第二段起就分叉**：集成分支 `squad/integration/<工作项>`、队员分支 `squad/member/<工作项>/<队员>`。**任何用路径层级命名的 ref 都受此约束。**
- **串行**合并（一次一个），避免竞态。
- **失败**：留分支 + 进 Inbox + 标 `blocked`。
- **合并后分支**：**删除**（队员分支与集成分支都删；集成分支在整批合回主分支之后删）；留痕靠工作项交付物 / diff 记录。

### 6.4 工作树约束

- 每队员**必须独立分支**（git 不允许两个 worktree 检出同一分支）。
- **单机运行**（决策 E）：不做多设备联动，「全员同 host」自动满足。
- **孤儿清理**：startup 时扫残留并回收——**清理是重派发的正确性前置**（孤儿 worktree 会占住分支，下次同分支再建会失败）。

### 6.5 run 级看门狗（第 8 项，完整）

空闲看门狗（后端静默且队列空）+ 工具看门狗 + 单次墙钟超时 + 取消 / 中断 + 失败重试 + 熔断。
**与 §5.5 的分工**：§5.5 拦「派发太频繁」，本节拦「一次 run 卡住不动」。

---

### 6.6 崩溃恢复、取消与并发

**启动时三项恢复**：
1. 回收**孤儿 worktree**（占住分支会导致重派发失败，属正确性前置）；
2. 把「进行中但宿主已消失」的 run 标为 `error` 并入 Inbox；
3. 重算唤醒规则的 `nextFireAt`——**漏掉的周期合并成一次**，不补跑全部。

**与现有 checkpoint 的关系**：小队路径**用 git worktree**；**checkpoint 不参与**，避免两套隔离叠加。现有 checkpoint 行为不变。

**并发**：同一工作项的多 run 受 §3.10 并发上限约束；**超限时新派发排队，而非丢弃**。

## 7. 记忆（决策 C4）

| 层 | 读写 | 内容 |
|---|---|---|
| 项目共享记忆 | **只读** | 「这个代码库是怎么回事」，所有 agent 共用 |
| 该智能体私有记忆 | **读写** | 各自的跨任务经验 |

- **路径分工**：智能体的**定义**放实验命名空间（§3.2）；**记忆**沿用 `agent-memory/<稳定 id>`。两者**都必须**进 §13 的排除清单。
- **leader 默认不读队员的私有记忆**；队员要让人/队长知道，必须**主动汇报**进共享通道——这是「独立交叉验证」的落点。

给定一个工作项（父）与一支小队（1 队长 + 2 队员）；当我把父项指派给小队；那么队长被唤醒一次并产出子工作项派发给 2 名队员；2 名队员各自在独立工作树执行；全部完成后再唤醒队长一次。

**S2 · 交叉验证生效**
给定 2 名队员写进**不同**会话；那么任一队员的会话中**不出现**另一队员的推理内容（上下文隔离）；队员只能通过共享沟通通道主动汇报。

**S3 · 防失控**
给定一条 `continuous` 唤醒规则且队长持续派单；当 run 次数达到 `maxFires`（默认 20）或一小时达到 12 次；那么该规则被暂停并记录 `pausedReason`，且**用户手动「现在就跑」不受此限制**。

**S4 · 合并与抛弃**
给定 2 名队员各自分支完成；当队长审查通过并合并；那么先合入 `squad/integration/<工作项>`，整批通过后合回主分支；随后工作树与分支**均被删除**；孤儿 worktree 在下次启动时被清理。

**S5 · 审查被拒不提前删**
给定某队员产出被审查打回；那么该队员的工作树**保持存活**直至修复并合并。

**S6 · 状态唯一写入**
给定用户、队长、调度器三方同时想改同一工作项；那么只有工作项服务写入；三方各自只发派发事件；最终状态唯一且流转幂等。

**S7 · 状态不驱动执行**
给定工作项被置为 `in_review`；那么**不自动**触发任何运行；只有匹配的唤醒规则 / 条件才触发。

**S8 · 关闭实验**
给定实验开关关闭；那么会话窗口的智能体入口、设置里的协作智能体与小队管理**整体消失**；现有 subagent / automation 行为**不受影响**。

**S9 · 不参与投射**
给定远程设备投射开启；那么投射端**不出现**小队 / 工作项界面。

**S10 · 归档交接**
给定某小队被归档；那么其工作项指派与排班**转移给队长**；归档的智能体在派发时被 **skip**（非失败）。

**S11 · 记忆隔离**
给定队员 A 与队员 B 各有私有记忆；那么 A 的私有记忆**不出现在** B 的上下文里，也不出现在 leader 的默认上下文里。

**S12 · automation 与唤醒规则分工**
给定一个「无工作项的定时任务」；那么它走 automation；给定一个「挂在工作项上的条件触发」；那么它走唤醒规则；两者不互相覆盖。

**S13 · 重复指派不重复唤醒**
给定同一工作项被重复指派给同一小队（且队长 run 仍在进行）；那么**只唤醒一次**（合并为同一次），不产生排队的第二次 run。

**S14 · 关闭实验不中断进行中的 run**
给定实验开关被关闭且此时有 run 正在执行；那么**新派发停止**，**进行中的 run 不中断**；入口隐藏但数据保留。

**S15 · 崩溃恢复**
给定进程在队友执行中崩溃后重启；那么孤儿 worktree 被回收；被中断的 run 标为 `error` 并入 Inbox；漏掉的周期规则**合并成一次**触发，不补跑全部。

**S16 · 并发超限排队**
给定单工作项并发 run 已达上限（默认 8）时又有新派发；那么新派发**排队等待**，**不丢弃**。

**S17 · 合并冲突**
给定两名队员的分支在集成分支上冲突；那么由队长 run 尝试解决；解决失败 → 工作项置 `blocked` + 进 Inbox，且**不会**提前合入主分支。

**S18 · 规则编辑的 fencing**
给定一条唤醒规则被编辑（`revision` +1）时有一批派发正在进行；那么**过期 revision** 的派发**自动作废**，不产生重复 run。

### P1 故意留白（需在接线前闭合）
